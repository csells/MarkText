- **Status:** Active; implementation and release verification incomplete.
- **Started:** 2026-09-05, following the owner's acceptance of the recovery recommendations.
- **Supersedes:** [0010](archive/0010-marktext-criticmarkup-core-integration.md), retired incomplete; [0009](archive/0009-criticmarkup-document-engine-rebuild.md) also remains incomplete.

## Outcome and retained scope

Deliver the existing MarkText editor with continuous, source-faithful CriticMarkup authoring and review in WYSIWYG. A complete editorial pass must remain editable after every accepted transaction, not merely render annotations or pass a scripted first edit. This plan carries forward the unfinished product, parity, safety, latency, and platform requirements of 0010; retiring its process does not complete those requirements.

Keep the upstream application shell, Muya presentation and widgets, CodeMirror Source mode, the custom language core, exact source mappings, transaction authority, Review UI, and independently grounded tests. Repair the integration instead of starting another editor rewrite. Replace an existing responsibility only when a reproduced product failure requires it and its replacement preserves the affected behavior.

All five canonical forms remain in scope: Addition, Deletion, Substitution, Highlight, and Comment. No proprietary syntax or metadata is required for this release. The separately proposed CriticMarkup Metadata Extension (working name CM2) is a **future milestone**: preserve its research and the user's domain decisions without implementing it here. Real-time collaboration, a reusable engine SDK, new external-file merge UX, and unrelated application redesign are also outside this plan.

## What changes from the previous approach

1. Lead with a failing everyday editorial interaction and complete one behavioral slice at a time. Test through the installed editor or its existing production interface, with an independent expected source and visible result.
2. Build a source-mapped, editable Markup adapter. A paragraph containing an annotation must not become an inert display or lose its caret after the first tracked character. Parser-owned ranges and boundaries, not ad hoc recognizers or serialized whole-document diffs, determine edits.
3. Preserve one semantic and durable document authority. One interpretation does not require one physical parser pass, a particular fork graph, or rewriting the product shell.
4. Restore full upstream parity incrementally, with ordinary behavior tests and a compact list of actual remaining gaps. A wiring test proves routing, not that the resulting interaction works.
5. Measure cold opening separately from sustained typing and editing in a running application. Keep repeatable observations and honest timing boundaries without requiring a fresh process for each typing sample.
6. Keep normal test reports, performance results, and installed smoke evidence. The old eight-decision approval packet, thousands of salvage dispositions, exact-hash attestations, exhaustive mutation proof, and fresh-profile-per-observation rules are superseded as completion prerequisites by the owner's accepted recovery direction. Existing records remain historical evidence, not a new approval queue.

Existing semantic decisions remain authoritative; this change does not silently ratify every historical Profile proposal. Resolve a genuinely disputed interoperability rule as a focused product decision when it affects implementation. Routine baseline selection, fixture maintenance, adapter design, and benchmark execution need no new approval ceremony. Do not change product meaning merely to match a parser or make a test green.

## Architecture and safety

- The framework-free core owns canonical decoded source, Markdown/CriticMarkup recognition, scoped syntax identity, source/view maps, validated atomic changes, and consistent projections. Incremental and full parsing produce equivalent observable results.
- One actor owns the acknowledged revision and undo history for each document. Revision-relative edits reject stale or unsafe targets explicitly; reused node identifiers cannot retarget a stale Review action.
- Muya and CodeMirror own presentation, selection, composition, widgets, and immediate pending drafts. They submit intent through the document authority and reconcile acknowledged changes. No view, Pinia snapshot, or speculative draft becomes save authority.
- Preserve bounded pending work, rejection recovery, immediate undo ordering, native IME, pending-save barriers, tab isolation, Source/WYSIWYG handoff, and Worker restart. Recover only acknowledged transactions; never silently drop input or publish partial failure.
- Ordinary edits update affected source and presentation without full-document reconstruction, hashing, transport, DOM replacement, or a main-process round trip on the typing path. Retain safe, explicit fallback for structural cases while improving measured bottlenecks.
- Main owns file bytes, encoding/BOM/EOL policy, atomic save and recovery, native effects, permissions, and safe exports. A no-op save is byte-exact; edited saves preserve unrelated source and declared file policy.
- Preserve finite documented resource limits and typed atomic rejection before unsafe allocation. Limits, data structures, and diagnostic counters remain implementation choices supported by measurements, not universal language rules.

During migration, Shadow is wholly upstream-authoritative and Core is wholly core-authoritative for a document session. Never select authority per operation. Keep production enablement gated by the product checks below, not by a document's approval-status field.

## Behavioral slices

Work red → green → refactor through one observed behavior at a time; do not write a speculative test matrix and then implement against it. A failing test must reproduce the product problem before the fix, or have an equivalent negative control. Retain useful existing coverage and report unsupported cases honestly.

### 1. Continue editing the same tracked paragraph

Open a fixture in the real editor, enable Track Changes, type a character, wait for acknowledgement, then continue typing in the **same paragraph**. Assert visible text, a usable caret, and exact canonical CriticMarkup source after both edits. Extend the slice to backspace, immediate undo/redo, Source/WYSIWYG handoff, save, close, and reopen. Use a throwaway fixture/profile and preserve user data.

The first green slice proves this interaction only. It does not complete all forms, structural editing, parity, or this plan.

### 2. Make Markup continuously editable

Route text and structural commands through parser-issued mappings, retaining selection and immediate presentation across acknowledged revisions. Expand from the first slice to typing around and inside additions, deletions, substitutions, highlights, and commented spans; multiline edits; selections crossing marks; paragraph/list/table boundaries; native cut/paste; and IME. Keep hidden Comment payloads outside caret navigation. A rendered annotation is not a substitute for an editable document.

Exercise stale/rejected edits, dependent drafts, save during pending input, undo/redo, tab switching, source changes, Worker restart, and delayed acknowledgements through the existing authority boundary. Preserve explicit outcomes and source/history integrity during failure.

### 3. Complete editorial workflows and consumers

Deliver the [native MarkText experience defined in the vision](../vision/criticmarkup-vision.md#what-native-integration-means), including the existing left sidebar and ordinary selection, menu, command, and history workflows. A separate functioning Review surface does not close this slice. Demonstrate all of the following through WYSIWYG and Source, with installed coverage for the full editorial pass:

- Faithful editable Markup and read-only Original/Revised projections; canonical standalone Highlight and Comment behavior; gapless Highlight+Comment presentation derived from current source adjacency.
- Selection-based Add Comment, comment editing/removal, passive selection, explicit Review focus/navigation, and target/draft preservation across cancel, stale revisions, validation, and submission failure.
- Isolated full Markdown+CriticMarkup Comment bodies, including local blocks, literals, definitions, references, footnotes, and nested annotations, without leaking state into surrounding or sibling content.
- Authoring every suggestion form and Track Changes for typing, deletion, cut/paste, replacement, formatting, structural operations, and IME; per-item and bulk accept/reject; source-exact undo/redo.
- Correct literal-context, cross-block, nesting, Unicode, empty-payload, and malformed-delimiter behavior according to the semantic contract.
- Declared projections for clipboard, search/replace, counts, HTML, PDF, print, and other shipped exports; safe untrusted rendering; exact save/reopen and mode switching without source drift or partial output.

Use canonical CriticMarkup examples, official CommonMark/GFM semantic outputs, and independently justified Profile expectations as oracles. Parser-produced fixtures can detect regression but cannot independently establish conformance.

### 5. Demonstrate realistic performance

Compare the pinned upstream and Core builds on the same recorded hardware with representative plain prose, Unicode, dense CriticMarkup, and math/diagram/image documents, including ordinary and larger working files. Measure cold open/first editable viewport separately from sustained typing, deletion, paste, navigation, and review in an already-open document. Include long editing sessions that expose queue growth, fallback cost, source fragmentation, and memory retention.

Record browser-input-to-visible-echo, authority acknowledgement, reconciliation, and a clearly described presentation observation. Do not label DOM checkpoints, animation callbacks, or screenshots physical paint. Preserve the user's background/non-focus-stealing test constraints while reporting their measurement limits; retain sample distributions, failures, build identity, environment, and progress.

Use existing proposed p95 targets as the initial comparison: echo 16.7 ms, dispatch 8 ms, acknowledgement/reconciliation 50 ms, open 500 ms, and first viewport 1,500 ms. Validate these against upstream and observed workload data; do not silently relax a target because Core misses it. Presentation measurement has no established numeric threshold yet: report its method and upstream comparison honestly rather than manufacturing a ratification wall. Ordinary interaction must have no perceptible typing lag, sustained backlog, or full-document work on each edit.

Separate cold-start samples from warm interaction samples; multiple warm edits may share one running app/profile. Extreme-size stress remains diagnostic unless it exposes unsafe admission, source loss, or an ordinary-workload failure. Optimize measured bottlenecks instead of implementing speculative parser machinery.

### 6. Enable and verify the product

After full editable Review behavior, affected upstream parity, source safety, and realistic performance pass, enable Core through the normal production entry path. Rebuild and verify the installed artifact with the feature available by default, without hidden test-only enablement. Exercise ordinary gestures, exact save/reopen, Source handoff, clipboard/search/export, IME, and recovery. Test controls may inject deterministic failures but cannot be the sole evidence for the shipped happy path.

Run required lint, type checks, core/language and desktop/Muya suites, production interaction tests, and applicable security checks against the final changes. Package and run equivalent installed smoke flows on macOS, Windows, and Linux; preserve concrete platform or environment blockers as unfinished work. Before an eventual PR submission, refresh against current upstream, account for changes, and rerun affected validation. This plan does not itself authorize commits, pushes, publication, or PR submission.
